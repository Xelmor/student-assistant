# Telegram Student Assistant: запуск и проверка

Бот использует существующее пространство сайта, включая пространство без пароля.
Отдельная регистрация, второй бот и дополнительные сервисы очередей не нужны.
Эта инструкция описывает код ветки `fix/telegram-integration`. Изменение кода или
Dockerfile само по себе не включает Telegram в Render.

## Что запускается

| Процесс | Локально | Render / публичный HTTPS |
| --- | --- | --- |
| Сайт | `python run.py` | Docker CMD `python run.py` |
| Получатель updates | `python -m telegram_bot.polling` | POST в веб-приложение, отдельный бот-процесс не нужен |
| Уведомления и повтор ожидающих ответов | `python -m telegram_bot.scheduler` | Отдельный постоянно работающий Background Worker |

Polling и webhook используют один обработчик и одну БД. Запускайте ровно один
polling-процесс; второй получит категорию `receiver_conflict`. Обычный запуск
polling сначала читает `getWebhookInfo` и отказывается работать при установленном
webhook. Он ничего не удаляет и не очищает очередь.

## Настройки без передачи секретов в чат и командную строку

Задавайте значения в защищённом окружении процесса или локальном `.env`, уже
исключённом из Git. Не вставляйте токен в URL браузера, аргументы shell или отчёты.
Рабочий `.env` при исправлении интеграции не изменялся.

| Настройка | Значение / назначение |
| --- | --- |
| `TELEGRAM_BOT_TOKEN` | Существующий токен из BotFather; резервное имя — `TELEGRAM_BOT_API_TOKEN` |
| `TELEGRAM_BOT_USERNAME` | Username именно этого бота без `@`; сайт строит ссылку из этого значения |
| `PUBLIC_BASE_URL` | Адрес сайта без пути; локально `http://127.0.0.1:8000`, публично HTTPS |
| `TELEGRAM_USE_WEBHOOK` | `false` для локального polling; `true` для публичного webhook |
| `TELEGRAM_WEBHOOK_BASE_URL` | Необязательное переопределение публичного HTTPS origin для webhook |
| `TELEGRAM_WEBHOOK_PATH` | `/telegram/webhook`, одинаковый при регистрации и в web-процессе |
| `TELEGRAM_WEBHOOK_SECRET` | Случайный секрет из `A-Z a-z 0-9 _ -`, 1–256 символов; рекомендуется не менее 32 |
| `DATABASE_URL` | Одна постоянная БД для web, polling и scheduler |
| `SECRET_KEY` | Постоянный секрет сайта, не менять при каждом деплое; минимум 32 символа |
| `APP_TIMEZONE` | Часовой пояс дат сайта и старых записей, по умолчанию `Europe/Moscow`; одинаковый во всех процессах |
| `TELEGRAM_LINK_CODE_TTL_MINUTES` | Срок Telegram-кода, по умолчанию 10 минут |
| `TELEGRAM_DIGEST_CHECK_INTERVAL_SECONDS` | Интервал scheduler, по умолчанию 60 секунд |
| `TESTING`, `DISABLE_TELEGRAM` | В реальном запуске `false`; тестовый режим намеренно обнуляет токен |

`TELEGRAM_BOT_API_BASE_URL` — **устаревшее имя публичного адреса сайта**, а не
адрес API Telegram. Оно сохранено только как последний fallback для регистрации
webhook. Приоритет: `TELEGRAM_WEBHOOK_BASE_URL`, затем `PUBLIC_BASE_URL`, затем
старое имя. Bot API использует `https://api.telegram.org`; адрес сайта туда
подставлять нельзя. `TELEGRAM_BOT_HOST/PORT` не запускают отдельный сервер webhook:
маршрут находится в основном приложении на `HOST/PORT`.

## Одна безопасная команда диагностики

Из корня проекта, в окружении проверяемого сервиса:

```bash
python -m telegram_bot.diagnose
```

Команда не выполняет миграции, не отправляет сообщения, не получает/подтверждает
updates и не меняет webhook. Показывает наличие настроек, режим, доступность БД,
отсутствующие таблицы, fingerprint адреса БД без пароля, число ожидающих/ошибочных
ответов и измеренный heartbeat scheduler. `not_observed`/`stale` не означает
«работает». `recent_completed` означает завершённый проход, а не успешную доставку
всех уведомлений. Наличие процесса-получателя не измеряется этой командой.

Только по явному запросу оператора разрешены два сетевых read-only метода:

```bash
python -m telegram_bot.diagnose --network
```

Это `getMe` и `getWebhookInfo`. Проверяются username, наличие/совпадение webhook,
`pending_update_count` и безопасная категория последней ошибки. Полный URL,
описание Telegram, токен и содержимое сообщений не печатаются. Для нового URL
нужен `webhook_matches=true`; для действующего старого endpoint допустимо
`webhook_legacy_matches=true`. В polling отсутствие webhook — нормальное состояние.

Fingerprint помогает сравнить настройки процессов, но не доказывает общность
SQLite: одинаковый путь на разных хостах означает разные файлы. Для PostgreSQL
проверяйте также имя БД/кластера в закрытой панели хостинга. Если сеть недоступна,
локальная диагностика и изолированные тесты всё равно доступны.

## Локальный запуск

Используйте Python 3.12. Существующий `venv` может быть устаревшим: `pip check`
не обнаруживает пакет, который вообще не установлен. Для нового локального
окружения macOS используйте constraints; production lock предназначен для
Linux x86_64 / Python 3.12 (см. `docs/testing/LINUX_CI.md`).

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -c requirements.constraints.txt -r requirements-dev.txt
python -m pip check
python scripts/ci/check_runtime.py
python -m telegram_bot.diagnose
```

В трёх терминалах из одного корня проекта и с одинаковыми настройками БД:

```bash
python run.py
```

```bash
python -m telegram_bot.polling
```

```bash
python -m telegram_bot.scheduler
```

Миграции запускаются штатно при старте каждого сервиса; перед первым включением
нескольких сервисов дайте web завершить миграции. Новые таблицы `telegram_updates`
и `telegram_state` создаются без удаления данных. Сначала проверяйте миграции
на временной БД/копии. Не запускайте локальный polling с production-токеном, пока
явно не решили переключить production-транспорт.

Если установлен webhook и вы **намеренно** переносите этого бота в polling,
остановите прежний получатель, задайте `TELEGRAM_USE_WEBHOOK=false`, затем явно:

```bash
python -m telegram_bot.set_webhook --delete-for-polling
python -m telegram_bot.polling
```

Флаг не очищает pending updates. Он не вызывается при старте, импорте, сборке
или тестах. Ctrl+C и SIGTERM завершают polling/scheduler.

## Подключение и команды

1. Откройте нужное пространство на сайте → профиль → «Подключить Telegram».
2. Нажмите «Открыть бота и подключить», затем Start в Telegram. Payload имеет
   вид `link_…`. Резервный вариант — скопировать `/link CODE` из профиля.
3. Убедитесь, что бот подтвердил название **того же пространства**.
4. Страница профиля опрашивает статус только в ожидании подключения: прекращает
   запросы после успеха, истечения кода, 10 минут или скрытия вкладки. После успеха
   страница обновляется с сохранением входа. Связь в БД и доступность бота различаются.
5. Включите нужные уведомления явно, выберите время/часовой пояс и отправьте
   тестовую сводку. Тест не включает автоматические уведомления.

Код одноразовый, новый отменяет предыдущий; 5 попыток привязки за 5 минут на
числовой Telegram ID. Создание кодов ограничено 5/5 минут на владельца, тестовые
сообщения — 3/минуту. Telegram-код не является QR-кодом устройства. Привязка
проверяется по ID, не username; чужая привязка не перезаписывается. Личные команды
и callbacks в группах не выдают данные и не меняют private chat ID.

Сохранены все команды: `/start`, `/help`, `/link`, `/today`, `/tomorrow`, `/week`,
`/tasks`, `/add_task`, `/cancel`, `/done`, `/notifications`, `/digest`, `/digest_on`,
`/digest_off`, `/digest_test`, `/site`, `/unlink`.

`/done N` работает по последнему показанному `/tasks` (30 минут), без fallback
на произвольный ID. Inline-кнопка хранит стабильный ID и повторно проверяет
владельца/состояние. Задачи и повторения используют тот же сервис завершения,
что и сайт. Пошаговое добавление хранится в БД 30 минут, новые кнопки содержат
версию диалога/шага. `/cancel` доступен на любом шаге. Отключение подтверждается;
оно выключает будущие уведомления, не удаляя задачи, пространство и QR-устройства.

## Надёжность и ограничения доставки

- Бизнес-операция, состояние диалога и ответ сохраняются одной транзакцией вместе
  с уникальным `update_id`. Повтор update не повторяет `/link`, создание задачи
  или переключение настройки. Необработанная ошибка возвращает webhook 503;
  подтверждение 200 возможно после обработки или надёжного сохранения ответа.
- Polling не двигает offset через упавший обработчик. Ожидающие ответы повторяет
  сам polling, а при webhook — scheduler. Блокировка отправки действует минимум 3 минуты (дольше для больших ответов)
  и восстанавливается после падения процесса.
- Ошибки различаются: `missing_token`, `invalid_token`, `blocked`, `chat_not_found`,
  `receiver_conflict`, `rate_limit`, `network`, `temporary`, `bad_request`.
  Текст Telegram/URL не логируется. Временные ответы повторяются не более 5 раз,
  учитывается `retry_after`; терминальная ошибка видна через диагностику/логи.
  После исправления конфигурации новую команду отправляет пользователь; старые
  терминальные ответы автоматически не рассылаются.
- Ответы старше 24 часов отменяются. Отвязка/смена владельца отменяет ожидающие
  персональные ответы. Успешно отправленный текст из outbox удаляется; остаётся
  небольшая запись `update_id` для дедупликации. Эти записи пока не очищаются
  автоматически: контролируйте размер БД. Диалог с истёкшим TTL не используется;
  его старое содержимое заменяется при следующем обращении.
- Сетевой timeout после фактической отправки и падение между отправкой и commit
  дают неопределённый результат: повтор **сообщения** возможен. Абсолютная
  exactly-once доставка не обещается. При длинном ответе части также могут
  повториться после частичной отправки; HTML безопасно преобразуется в plain text
  и разбивается по лимиту. Изменение задачи при этом не повторяется.
- Блокировки scheduler удерживаются до ответа API и записи журнала. Это защищает
  от двух worker; SQLite на время сети ограничивает запись другим процессам,
  поэтому для нескольких production-процессов используйте PostgreSQL.

## Уведомления и время

Согласие проверяется непосредственно перед отправкой. Сводка использует выбранный
часовой пояс с fallback `APP_TIMEZONE` / `Europe/Moscow`. В `/today`, `/tomorrow`
и `/week` используется дата пользователя. Хранящиеся на сайте naive-дедлайны
интерпретируются в `APP_TIMEZONE`, а не в часовом поясе машины; изменение timezone
сводки не сдвигает момент дедлайна сайта. Календарные отмены и каникулы учитываются.

Сводка догоняется только в течение двух часов после заданного времени; за прошлые
дни ничего не отправляется. Напоминания касаются только незавершённых задач с
будущим дедлайном внутри выбранного окна 2/6/24 часа, максимум три на пользователя
за проход. Просроченные/удалённые/завершённые задачи не догоняются. После перезапуска
журнал в БД предотвращает повтор подтверждённых отправок. Запись успеха создаётся
после ответа Telegram. `blocked`/неверный токен не повторяются для той же привязки
и токена; после разблокировки при необходимости отключите и подключите связь
заново. Не удаляйте журнал для «починки» — это вызовет повторы.

## Render: отдельный чек-лист включения

1. Проверьте выбранный репозиторий/ветку/HEAD вручную. Из этой задачи не выполнялись
   commit, push, merge или deploy. Сохраните резервную копию БД перед обновлением.
2. Web-сервис использует текущий `Dockerfile`: установка
   `pip install --require-hashes -r requirements.lock.txt`, затем `pip check`.
   Команда контейнера — `python run.py`, `HOST=0.0.0.0`, порт из Render `PORT`.
   Проверьте build log: используется production lock, а не свободный `requirements.txt`.
3. Настройте `APP_ENV=production`, `COOKIE_SECURE=true`, постоянный `SECRET_KEY`,
   корректный `PUBLIC_BASE_URL`, разрешённый hostname, `RELOAD=false`,
   `TESTING=false`, `DISABLE_TELEGRAM=false`, `TELEGRAM_USE_WEBHOOK=true`.
4. Web и scheduler должны подключаться к **одной постоянной PostgreSQL БД** с
   одинаковыми Telegram-настройками и `APP_TIMEZONE`. Одинаковая строка
   `sqlite:///…` у разных Render-сервисов не объединяет их данные.
5. Дайте web запуститься и применить миграции. Проверьте диагностику таблиц, затем
   явно зарегистрируйте webhook и команды (ниже). Не запускайте polling параллельно.
6. Отдельный worker запускает `python -m telegram_bot.scheduler`. Убедитесь через
   диагностику, что heartbeat свежий. Без реально работающего worker своевременные
   уведомления и повторы ответов webhook не гарантируются.
7. Проверьте настоящий сценарий владельца: код сайта → Start/link → имя пространства
   → задачи → создание/закрытие одной тестовой задачи → изменение на сайте → тест
   сводки → выбранное время → отключение. Не делайте массовую тестовую рассылку.

Явные setup-команды, только после настройки защищённого окружения:

```bash
python -m telegram_bot.diagnose
python -m telegram_bot.diagnose --network
python -m telegram_bot.set_webhook
python -m telegram_bot.set_commands
python -m telegram_bot.diagnose --network
```

Setup-команды не требуют соединения с production-БД. Если Render Shell недоступен,
выполните их локально из этой версии кода с безопасно настроенными Telegram и
публичными адресами Render. Не используйте локальный адрес сайта для этой операции,
не запускайте одновременно polling; токен не передаётся в аргументах команд.
Диагностика БД из локальной среды относится к **локальной** БД, если отдельно не
настроено подключение к той же production-БД.

При переносе существующей локальной SQLite: не начинайте с пустой production-БД
незаметно для пользователя. Остановите записи, сделайте защищённую копию, выполните
пробный перенос всех таблиц с сохранением ID/связей (включая users, workspaces,
workspace_devices, Telegram-связи, журналы и состояние) в тестовый PostgreSQL,
сверьте количество записей и доступ устройств. Только после проверки переключайте
web и worker вместе. Универсальный автоматический перенос SQLite→PostgreSQL эта
Telegram-доработка не выполняет. Экспорт учебных данных сам по себе не переносит
все устройства и привязки.

### Совместимость webhook

Новая регистрация использует `https://<ваш-сайт>/telegram/webhook` и заголовок
`X-Telegram-Bot-Api-Secret-Token`. Старый маршрут `/telegram/webhook/<secret>`
сохранён с проверкой прежнего секрета. Если прислан и заголовок, он также должен
совпадать. Сначала обновите приложение с обоими endpoint, затем явно выполните
`set_webhook`. Не меняйте действующий секрет до согласованного переключения.
Встроенные application/uvicorn/httpx-логи скрывают legacy URL; внешние access-логи
reverse proxy контролируются хостингом, поэтому переход на заголовок предпочтителен.

### Бесплатный тариф и фоновые процессы

По документации Render, Free web засыпает после 15 минут без входящего трафика;
следующий запрос будит сервис с задержкой. Файлы локальной SQLite на ephemeral
filesystem теряются при перезапуске/деплое/сне. У Free web нет Shell/SSH и постоянного
диска. Поэтому бесплатный web не заменяет постоянно работающий scheduler.
Background Worker требует подходящего оплачиваемого compute либо отдельного
реально работающего хоста с доступом к общей БД. Ресурсы и тарифы в этой задаче не
создавались и не менялись; self-ping не добавлен.

Источники, проверенные 29.09.2026:
[Render Free](https://render.com/docs/free),
[Shell/SSH](https://render.com/docs/ssh),
[типы сервисов](https://render.com/docs/service-types),
[тарифы](https://render.com/pricing),
[Telegram Bot API](https://core.telegram.org/bots/api#setwebhook).

## Изолированные проверки

В окружении тестов должны быть `APP_ENV=test`, `TESTING=true`,
`DISABLE_TELEGRAM=true` и временная `DATABASE_URL`. Тесты используют фиктивные
данные, временные SQLite и управляемые моки API. Это не live-проверка настоящего бота.

```bash
python -m pytest -q
python -m pytest -q tests/e2e --browser chromium
python -m pip check
python scripts/ci/check_runtime.py
python -m compileall -q app telegram_bot tests
node --check app/static/js/profile-telegram.js

```

Сохранены четыре CI job. Linux x86_64, production Docker image и PostgreSQL нужно
дополнительно подтвердить в соответствующей среде; локальный macOS-прогон этого
не доказывает. Секреты, токены, коды, recovery keys и cookies в отчёты не включайте.

## Напоминания перед занятиями и snooze

В Telegram: «⚙️ Настройки» → «🎓 Пары». По умолчанию выключены;
интервал — 15 минут, доступны 10/15/30/60. Публичных slash-команд по-прежнему шесть.

Хранение в существующей `telegram_state`, без миграции схемы:

- `class-settings:<user_id>`: независимые `enabled` и `lead`, без срока истечения.
- `class-event:<user_id>:<hash>`: occurrence, дата/фактическое начало, timezone,
  привязка Telegram, статус исходного уведомления; `snooze_due` в UTC и
  `snooze_status` для единственного snooze. Повторная кнопка не переносит его срок.
- `class-send:<hash>` / `class-snooze-send:<hash>`: существующий формат состояния
  доставки scheduler, попытки, backoff, terminal/sent. Неизвестные ошибки транспорта
  также получают ограниченный retry; максимум пять попыток, минимум 60 секунд,
  учитывается Telegram `retry_after`. Blocked/неповторяемые ошибки не ретраятся.

Тот же `telegram_bot/scheduler.py` проверяет занятия через `TelegramCalendar`
из `telegram_day.py`. Отмена/перенос обрабатываются общим календарём. Добавлен
только стабильный `schedule_item_id` в событие обычного расписания.
Проверяются сегодня и завтра в timezone пользователя (с существующим fallback
на timezone проекта). Обнаружение допускает опоздание до пяти минут включительно;
после начала исходное уведомление уже не отправляется. Обнаруженные pending
уведомления можно повторить и после пяти минут, пока пара ещё не началась.

Дедупликационный ключ включает пользователя, источник occurrence, локальную дату
и фактическое начало, lead time, тип уведомления, timezone и текущую привязку.
Snooze имеет отдельный ключ доставки. Блокировка строки удерживается до отправки
и commit, поэтому обычные повторные проходы, рестарты и конкурирующие workers
не создают повторную доставку. Перед каждой отправкой проверяются согласие,
привязка и актуальное расписание. Старый snooze не переносится на новую привязку.
Задачи и их дедлайны не меняются.

Snooze запланирован на 10 минут после нажатия. При уже начавшейся паре сообщение
сообщает об этом и предлагает «📍 Сейчас». Отменённая/удалённая/завершившаяся пара
не отправляется. Перенос в тот же день до 60 минут включительно использует
актуальные данные; более значительный перенос или другой день отменяет старый
snooze. Новое исходное напоминание при этом может прийти по новому расписанию.
После простоя snooze допускает задержку до 10 минут, затем считается устаревшим.

Ограничения: scheduler должен реально работать и использовать общую постоянную БД.
Абсолютное exactly-once на границе Telegram/БД невозможно: если Telegram принял
сообщение, а процесс завершился до commit или ответ потерялся, retry может
повторить сообщение. Конкурентность проверяется локально на SQLite; отдельный
PostgreSQL-прогон в этой среде не выполнялся. Occurrence-записи перестают
участвовать в выборке через восемь дней, но автоматически физически не удаляются.

## Быстрые заметки из Telegram

«📝 Заметка» → одно текстовое сообщение → сохранение без дополнительных вопросов.
Альтернатива: `заметка: на БД повторить оконные функции`. Без явного префикса
обычный текст вне режима заметок сохраняет существующее поведение задач.
В публичном меню остаются шесть команд, `/note` не добавляется.

Используется существующая модель `Note` из `app/models/note.py`, та же таблица,
что у `/notes`, и `normalize_bounded_text` с ограничениями сайта. Первая строка
до 60 символов становится заголовком, остальные строки — содержимым. Если первая
строка длиннее, заголовок становится коротким фрагментом, а полный текст остаётся
в `content` (до 10 000 символов). Как и на сайте, внешние пробелы убираются.
Telegram preview ограничен 200 символами и экранирован для HTML. Превышение
лимита возвращает ошибку, данные молча не обрезаются.

Ожидание текста хранится в `telegram_state` под ключом `note-flow:<telegram_id>`:
владелец, привязка, случайный token кнопки отмены, TTL 30 минут. Текст заметки
не дублируется в этом состоянии. По истечении TTL следующий текст получает
сообщение об устаревшем создании и не попадает в task parser. `/cancel`, кнопка
отмены и слово «отмена» закрывают flow. Старый token отмены не закрывает новое
ожидание. Рестарт процесса не теряет состояние.

Маршрутизация: активный специальный перенос задачи → заметка (ожидание или
явный префикс) → существующий task/edit flow → conversational intents → task
parser. Обычный черновик задачи сохраняется, если поверх него открыть заметку;
после заметки его можно продолжить. В режиме заметки «привет»/«спасибо» являются
текстом заметки. Операции доступны только привязанному пользователю в private chat.

Кнопка удаления читает актуальную запись с проверкой владельца и показывает
подтверждение. `note-delete:<user_id>:<note_id>` хранит только token, привязку и
отпечаток версии на 30 минут. Перед удалением заново проверяются владелец,
подтверждение и текущая версия. Если сайт изменил запись, требуется подтвердить
новую версию. Если сайт уже удалил запись, старая кнопка отвечает, что заметки
нет. Повторный callback безопасен. Идемпотентность создания использует существующий
`TelegramUpdate`/outbox; повтор доставки одного update не создаёт вторую Note.

Ограничения: поддерживается один текстовый Telegram message, без вложений,
голоса и объединения нескольких сообщений. Префикс распознаётся только с
двоеточием. Одинаковый текст, отправленный новым отдельным сообщением с префиксом,
считается намеренным созданием новой заметки. Ранее отправленный Telegram preview
сам не редактируется, но кнопки всегда обращаются к текущей записи сайта.

## Вечерняя сводка

«⚙️ Настройки» → «🌙 Вечерняя сводка»: независимое от утренней сводки включение,
по умолчанию выключено, время 21:00. Доступны 19:00/20:00/21:00/22:00.
«🧪 Показать сейчас» строит реальную сводку без включения автоматической доставки
и без отметки об отправке. Кнопки digest вызывают существующие `tomorrow`, `tasks`
и `note_start`. В публичном menu остаются шесть команд.

Данные собирает `telegram_evening_digest.py`:

- `Task.completed_at` уже существует; общий `complete_task()` сайта и Telegram
  записывает его во времени проекта, без tzinfo. Границы текущего локального дня
  пользователя переводятся в `APP_ZONE` перед запросом. Учитываются только
  завершённые задачи с известной датой выполнения, не позже текущего момента.
  Восстановленные задачи не считаются выполненными. Исторические NULL не
  подменяются датой создания или дедлайном. Миграция не нужна.
- Активные задачи и их порядок — `telegram_task_views.active_tasks`; просрочка —
  существующий `_task_rank` из `telegram_today`, но только для задач с настоящим
  `Task.deadline`. Дата планирования без дедлайна не считается просрочкой.
  Завтрашние дедлайны считаются по `Task.deadline` (локальные значения пользователя),
  без выполненных задач и без подмены дедлайна обычной датой планирования.
- Завтрашние занятия — `TelegramCalendar` из `telegram_day`, с общими отменами и
  заменами. Показывается только число и первая пара. При неполном времени
  выводится пояснение, а не выдуманное 00:00.
- «Не забудь» содержит максимум одну задачу: просроченная → дедлайн завтра →
  высокий приоритет → ближайший дедлайн. Пустые счётчики не выводятся.

Настройки: `telegram_state`, ключ `evening-settings:<user_id>`, поля `enabled`
и `hour`, без срока истечения. Факт доставки и retry: отдельная строка
`evening-digest:<user_id>:<local_date>`. Тип сводки входит в ключ, поэтому утренняя
и вечерняя доставки независимы. Изменение выбранного часа после успешной отправки
не даёт второй сводки в тот же день.

Существующий scheduler выбирает только включённые настройки в БД и вызывает
сервис в общем tick/heartbeat. Сбор данных и чистый renderer находятся в сервисе;
отправка и фиксация результата — в `telegram_bot/scheduler.py`. Отправка использует
его `_send_notification`: persistent retry/backoff, `retry_after`, максимум пять
попыток, blocked и другие постоянные ошибки без повторов. Успех записывается
только после успешного send. Блокировки БД удерживаются до отправки и commit,
что проверено двумя конкурентными workers и рестартом процесса. Preview проходит
обычный reply outbox и не изменяет автоматический журнал. Кнопка «← Назад»
из preview возвращает в настройки вечерней сводки; автоматическая сводка
содержит только Tomorrow/Tasks/Note. Перед автоматической
отправкой проверяются настройки и активная привязка; отрицательные group chat id
не используются. Ошибка одного адресата не останавливает остальных.

После простоя допускается опоздание до 15 минут, только в тот же локальный день.
Вчерашняя сводка после полуночи не догоняется. Retry заново строит сообщение по
актуальным данным и также ограничен этим окном. Настройки используют существующий
timezone пользователя (`telegram_morning_digest_timezone`) с fallback проекта;
системный timezone хоста не используется.

Ограничения: произвольное время пока не поддерживается. Дата выполнения старых
задач с NULL неизвестна, такие задачи не входят в дневной счётчик. При потере
ответа Telegram/аварии после отправки до commit возможна повторная доставка —
абсолютного exactly-once между внешним API и БД нет. Локальные конкурентные тесты
выполнены на SQLite, отдельный PostgreSQL/live Telegram прогон не выполнялся.
Настройки и журнал требуют общей постоянной БД; старые дневные записи журнала
автоматически не удаляются.

## Недельный обзор

`/week` и «🗓 Неделя» открывают краткий обзор календарной недели. Кнопки ведут
к следующей неделе, полному расписанию, задачам и главному меню. Старый экран
событий и ближайших пяти дедлайнов сохранён через «📋 События и дедлайны»
(`week_details`). Публичных slash-команд остаётся шесть.

Данные собирает `telegram_weekly_digest.py`:

- Неделя определяется в существующем timezone пользователя: понедельник 00:00
  включительно — следующий понедельник 00:00 исключительно. Диапазоны корректно
  переходят границы месяца/года. Завершённые задачи выбираются по `completed_at`:
  локальные границы переводятся во время проекта, как для вечерней сводки.
  NULL и даты в будущем не включаются. Для будущей недели счётчик не показывается.
- Все семь дней читаются через `TelegramCalendar` из `telegram_day`. Отменённые
  занятия не входят, перенесённые относятся к фактической дате. Учебное время —
  сумма длительностей занятий, переведённых в UTC с timezone пользователя:
  это учитывает DST. Формат интервала переиспользует `format_interval`.
  Неизвестная/некорректная длительность не выдумывается: показывается сумма
  известного времени с пояснением. Количество включает все записи занятий.
- Активные задачи и сортировка переиспользуют `active_tasks`, просрочка —
  `_task_rank` с обязательным `Task.deadline`. Главное для текущей недели:
  просроченная → дедлайн сегодня → ближайший дедлайн выбранной недели → высокий
  приоритет → ближайший будущий дедлайн. Для следующей недели главное выбирается
  только среди её невыполненных задач с дедлайном; текущая просрочка не заслоняет
  будущий обзор.
- Расписание содержит все семь дней и пагинируется по строкам. Бюджет страницы —
  3000 UTF-16 единиц HTML-исходника плюс короткий заголовок, с запасом до лимита
  Telegram. Заголовок дня повторяется на новой странице; emoji/HTML экранируются.
  Дата недели включена в callback: кнопка воскресного обзора после понедельника
  всё ещё открывает ту же неделю. Даты вне диапазона ±52 недели отклоняются.

«⚙️ Настройки» → «📊 Недельный обзор»: по умолчанию выключено, воскресенье 19:00.
Доступны пятница/суббота/воскресенье и 18:00/19:00/20:00/21:00.
Настройки хранятся в `telegram_state`, `weekly-settings:<user_id>`:
`enabled`, `day`, `hour`, без срока истечения. Утренние, вечерние сводки и
напоминания не меняются. Preview строит автоматический обзор следующей недели,
не включая доставку и не меняя журнал отправки.

Автоматическая отправка использует существующий scheduler и общий с вечерней
сводкой `_process_periodic_digest`, без отдельного scheduler/retry-механизма.
Выбираются только включённые настройки и активные private-привязки. Окно —
15 минут после выбранного времени в выбранный локальный день. Ключ доставки:
`weekly-digest:<user_id>:<понедельник_предстоящей_недели>`.
Изменение дня с пятницы на воскресенье не создаёт вторую отправку для той же
предстоящей недели. Блокировки БД, успешный commit, bounded retry/backoff и
обработка blocked переиспользуются. Ошибка одного пользователя не останавливает
остальных; после unlink новые сообщения и retries не отправляются.

Ограничения: суммируются длительности записей, а не фактическая посещаемость;
пересекающиеся занятия учитываются отдельно. Для двусмысленного времени при
осеннем DST используется первое вхождение (`fold=0`), поскольку исходная модель
расписания не хранит fold. Несуществующее время весеннего перехода не входит в
сумму. Очень длинные названия в Telegram сокращаются, данные в БД сохраняются.
Пропущенное 15-минутное окно не догоняется позже. При потере ответа API после
доставки или аварии до commit возможен дубль; абсолютного exactly-once нет.
PostgreSQL и официальный клиент Telegram отдельно не проверяются локальными
тестами. Старые delivery-строки автоматически не удаляются.

## Универсальный поиск Telegram

«🔎 Поиск» в главном меню открывает ввод одного запроса. Также доступны
`поиск: <запрос>` и `найти: <запрос>` без предварительного нажатия кнопки.
Публичных slash-команд по-прежнему шесть. Поисковый текст не создаёт задачи.

`app/services/telegram_search.py` читает существующие записи сайта; отдельного
индекса, таблиц, копий результатов и AI/LLM нет:

- `Task`: title, description и название принадлежащего пользователю Subject.
  Активные выше выполненных. Внутри каждой группы: точное название → начало
  названия → подстрока/все токены в названии → все токены в совокупности полей.
  При равенстве: просроченные → сегодня → ближайший дедлайн → без дедлайна,
  затем id для стабильного порядка. Выполненные помечены «✅ Выполнено».
- `Note`: полный title/content. При одинаковой релевантности свежие выше.
  Выдача содержит короткое название и preview, исходный текст не сокращается.
- Занятия: существующий `TelegramCalendar` / `calendar_service`, включая отмены
  и переносы. Поля: название занятия, название предмета, аудитория занятия,
  преподаватель Subject. Показываются только occurrences с началом не раньше
  текущего момента, в диапазоне от сегодняшней локальной даты включительно
  до даты +30 дней исключительно. При равной релевантности ближайшие выше.
  Предмет без будущего занятия может найтись через связанную задачу; отдельных
  карточек предметов нет. Аудитория и преподаватель не выдумываются.

Нормализация: Unicode NFKC + casefold, ё→е, пунктуация/символы заменяются
пробелами, лишние пробелы схлопываются. Минимум два непробельных буквенно-цифровых
символа, максимум 200 символов исходного запроса. Поиск токенизированный и
substring: «бд» не является автоматическим синонимом «базы данных», опечатки,
склонения и семантика не распознаются.

Первый экран — максимум 5 результатов каждой категории. «Ещё задачи/заметки/
занятия» показывает следующую пятёрку соответствующей категории. При каждом
переходе данные заново запрашиваются у владельца; обновления на сайте видны
сразу, но изменение данных между страницами может сдвинуть позиции результатов.
Заголовки и preview ограничены по UTF-16 длине экранированного HTML. Даже полная
смешанная выдача с emoji и HTML остаётся меньше лимита Telegram. Длинное название
сокращается только в сообщении. Кнопка «📅 Расписание» открывает существующую
неделю, откуда доступно полное расписание; «📝 Заметка» создаёт новую заметку.

Диалог хранится в `telegram_state`, `search-flow:<telegram_user_id>` со
`state=waiting_for_search_query`. Запрос для пагинации хранится отдельно в
`search-results:<telegram_user_id>`; содержимого задач/заметок там нет. TTL обеих
записей — 30 минут. Перезапуск процесса не сбрасывает ввод. После результата
состояние ожидания очищается; слишком короткий/длинный запрос можно исправить.
Истёкшее ожидание отвечает «⚠️ Поиск устарел.» и не передаёт текст парсеру задач.
`/cancel`, «❌ Отмена» и текст «отмена» закрывают диалог. `/start` также закрывает
ожидание. Старые кнопки отмены не отменяют новый поиск.

Активный перенос задачи и существующий диалог заметки сохраняют приоритет.
Активное редактирование/пошаговое создание задачи не перехватывается поиском:
кнопка предлагает сначала завершить действие или отменить его. Ожидание поиска
обрабатывается до явных префиксов и conversational intents: «привет» становится
запросом. Существующее поведение явного `заметка:` внутри редактора задачи
сохранено. В обычном режиме `поиск:`/`найти:` обрабатываются до natural-language
parser. Поиск и выдача ничего не меняют в задачах, заметках и расписании.

Безопасность: общий guard бота отклоняет группы до обработки поиска. Пользователь
определяется по привязанному Telegram sender; каждый SQL-запрос ограничен его
user_id, включая join предмета. Доступ к данным не определяется callback-параметром.
В состояниях сохраняются текущая привязка и случайный token; после перепривязки,
истечения TTL или подстановки чужого token старые callbacks отклоняются.
Непривязанному пользователю показывается существующий вход подключения.

Ограничения первой версии: Python-фильтрация читает принадлежащие пользователю
записи без полнотекстового индекса; для очень большого персонального архива
потребуется отдельная оптимизация. Горизонт календаря ограничен 30 локальными
датами. Занятие без известного начала сегодня не выдаётся как гарантированно
будущее; на последующих датах время показывается как неуказанное. Двусмысленное
время DST использует первое вхождение, как существующая модель расписания.
TTL-строки автоматически не удаляются. E2E проверяет webhook/БД в тестовом
HTML-viewer на 1440/390 px с подменённой отправкой, а не официальный клиент Telegram.
